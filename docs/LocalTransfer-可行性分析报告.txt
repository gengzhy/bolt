# LocalTransfer 本地离线高速跨端文件传输助手
## 基于Rust统一底层全端方案（方案4）可行性分析报告
文档编号：LT-RUST-REVIEW-20260827
评审对象：《本地文件传输助手-需求分析报告》（LT-RUST-REQ-20260827）
文档性质：技术评审 / 需求修订依据，供需求文档修订与项目启动决策使用

## 一、总体结论

方向可行，但当前需求文档尚不能作为"唯一编码基准"直接开工。

1. 可行性判断：可行。同类产品的技术路线（对标 LocalSend、LANDrop、AirDrop 类工具）
   已在业界被充分验证，"Rust 统一网络/文件核心 + 各平台薄 UI 层"的分层思路正确，
   具备落地条件；
2. 文档质量判断：架构分层、模块划分、FFI 规范、错误码体系设计清晰合理（约85分）；
   但协议报文设计、安全信任模型、平台能力假设存在硬伤（约60分）；
3. 核心结论：存在 6 处必须修正的阻塞项（技术矛盾或平台事实性错误）、若干协议设计
   缺陷，以及 1 个关键产品级缺失（配对与接收确认的安全模型）。必须先修订阻塞项，
   再进入脚手架搭建与编码，否则协议一旦在多端实现后再改，返工成本为当前的十倍以上。

## 二、必须修正的问题（阻塞项，共6项）

### 2.1 "QUIC 明文模式"技术上不成立【协议/架构矛盾】
原需求2.2节要求"高速明文模式：关闭TLS加密"，同时主传输协议为QUIC。
问题：QUIC（RFC 9000）在协议栈层面强制内嵌 TLS 1.3，无法关闭加密；
quinn 等主流实现也不提供无加密 QUIC 连接。
修正建议（二选一）：
    方案A：明文模式仅走裸 TCP（无加密），加密模式走 QUIC；
    方案B（推荐）：取消明文模式。千兆局域网下 AES-GCM 依托 AES-NI / ARMv8 加密
    指令集硬件加速，吞吐损失通常小于5%，不值得为此保留一套降级路径；且咖啡厅、
    酒店等开放/半开放WiFi环境下明文传文件是真实安全风险。

### 2.2 私有协议报文结构存在设计缺陷【协议核心缺陷】
原需求2.3节的固定报文结构问题如下：
    （1）缺少分片序号字段：0x02分片报文无法定位写入偏移，断点续传"携带已完成
         分片索引"无从落地，属协议核心字段缺失；
    （2）缺少任务/会话ID：多文件并发、双向互传场景下无法区分报文归属任务；
    （3）所有报文强制携带文件元数据：心跳（0x07）、ACK（0x03）等报文也要背负
         文件名+32字节MD5，结构不合理；
    （4）缺少相对路径字段：2.4节要求多层文件夹传输，但协议仅有"文件名称"，
         无法在接收端重建目录树；
    （5）缺少控制面消息：现有0x01~0x07均为数据面指令，缺少传输请求、对端接受/
         拒绝、文件元数据预告（大小/路径/修改时间）、错误通知等消息；
    （6）无协议版本扩展机制：0x01提到"协商协议版本"，但未定义未知指令的兼容规则，
         后续升级将被锁死。
修正建议：报文改为"[4字节总长][1字节指令][4/8字节序列号或任务ID][载荷]"，
载荷按指令码分别定义；文件元数据（相对路径、大小、修改时间、校验算法标识）
作为独立控制消息先行交换；预留保留字段与未知指令忽略规则。

### 2.3 安全信任模型完全缺失【关键产品级缺口】
原文档仅区分"加密/不加密"，未回答以下三个安全问题：
    （1）证书来源：加密模式必然使用自签证书，需要"首次启动生成密钥对+证书、
         本地持久化"的完整管理流程；
    （2）中间人防护：自签证书无信任锚，需要配对确认机制——对端确认弹窗
         （AirDrop式）、6位配对码/短认证码（SAS）比对，至少实现首次信任（TOFU）；
    （3）接收方确认：当前设计下局域网内任何设备均可直接向本机写入文件，
         必须实现"接收请求 → 用户同意/拒绝"流程。
修正建议：将配对/接收确认模型纳入需求2.6交互流程与2.2握手流程，作为一期强制功能。

### 2.4 WiFi Direct 与 iOS 平台能力冲突【事实性错误】
原需求1.3、3.3节将WiFi Direct列为全端兼容场景。
事实：iOS 从未开放 WiFi Direct API（AirDrop 为苹果私有实现）；且 WiFi Direct 的
组网协商（Android Wi-Fi P2P）与"同一二层网络 + mDNS 发现"模型完全不同，
等于需要第二套发现/组网机制。
修正建议：从首版范围移除 WiFi Direct，或明确标注"仅Android、后期版本支持"。

### 2.5 iOS 后台传输期望不符合平台现实【事实性错误】
原需求2.6、3.2节要求"锁屏保活、断连自动重连续传"。
事实：iOS beginBackgroundTask 仅约30秒~3分钟窗口；BGTaskScheduler 为系统调度的
碎片化后台机会，均无法支撑大文件持续传输。iOS 锁屏/切后台后传输必然中断。
修正建议：iOS 端明确"传输需保持前台"，以断点续传兜底（回到前台自动恢复）；
72小时稳定性测试目标按平台分别定义（iOS不考核锁屏连续传输）。

### 2.6 构建工具链选型错误【事实性错误】
原需求4.3节"cross预编译Android .so / 编译iOS xcframework"。
事实：cross 是面向 Linux 容器的交叉编译工具，不支持 iOS，Android 也非主流路径。
修正建议：
    Android：使用 cargo-ndk 编译 aarch64-linux-android / x86_64-linux-android；
    iOS：在 macOS 上用 cargo 直接编译 aarch64-apple-ios（含模拟器target），
         使用 cargo-xcframework 或自定义脚本组装 xcframework；
    CI：iOS 构建必须使用 macOS Runner，Android 可用 Linux/Docker Runner。
该项为脚手架阶段的第一个实际障碍，需在文档中直接更正。

## 三、需要优化的设计点（共9项）

### 3.1 "每分片停等ACK"拖累吞吐
原流程3"每发送一块等待远端ACK确认"为停等协议：千兆下1MB分片发送约8ms，
叠加RTT将损失10%~25%吞吐，且与QUIC自身可靠传输机制重复。
优化建议：QUIC模式依赖流的可靠交付，接收端改为周期性累积确认（如每200ms或
每N MB回报一次已收偏移），发送端据此更新断点进度；ACK语义定位为"进度记账"
而非"可靠性机制"。

### 3.2 MD5 预计算成为100GB大文件启动瓶颈
单线程MD5约400~500MB/s，100GB文件预哈希需3~4分钟才能开始传输，与"快速响应"
指标矛盾；且MD5已不适合完整性证明（可构造碰撞）。
优化建议：
    （1）哈希算法更换为 BLAKE3（多线程可达数GB/s）或 SHA-256；
    （2）取消传输前全量预计算，改为边传边算/分块哈希（Merkle式）；
    （3）续传文件身份识别改用"路径+大小+修改时间"组合，不依赖全量哈希。

### 3.3 mDNS 平台差异被低估
    （1）Android：应用接收组播报文必须先获取 WifiManager.MulticastLock，
         原文档未提及；部分系统版本限制应用绑定5353端口（系统mDNSResponder占用），
         建议同时提供系统 NSD（NsdManager）路径；
    （2）iOS：应用自绑5353实现mDNS会与系统服务冲突，正规路径为 Network.framework
         的 NWBrowser（Bonjour），由Swift层发现后将设备列表传入Rust——该例外
         需在4.1分层规范中明确；
    （3）通用兜底：建议增加轻量UDP广播/子网探测发现机制。mDNS在企业网、
         组播被防火墙拦截的环境下会整体失效，仅靠手动输入IP体验过差。

### 3.4 BLE 辅助发现落地成本高
"Rust底层封装BLE"跨Android（BluetoothLeAdvertiser/Scanner）与iOS（CoreBluetooth）
工作量大，跨端库成熟度一般（可评估btleplug）。且逻辑闭环上，BLE仅在"一方已开
热点、存在可交换的IP"时有意义。
优化建议：降级为二期特性；一期以"手动IP直连 + UDP广播兜底"覆盖无WiFi场景。

### 3.5 Android 前台服务新约束
    （1）Android 14+ 必须声明 foregroundServiceType="dataSync"；
    （2）Android 15 对 dataSync 类前台服务引入约6小时运行时限，72小时连续传输
         目标在Android 15+上无法由单一前台服务达成，需设计"服务被杀→自动恢复+
         断点续传"路径；
    （3）需补充 WakeLock/WifiLock、Doze 电池优化白名单引导逻辑。

### 3.6 性能指标需加限定条件
    （1）WiFi6"单文件≥800Mbps、并发≥1.1Gbps"仅在160MHz频宽、近距离、高质量
         终端的实验室条件下可达。建议标注为"峰值目标"并补充"典型值"
         （实际常见400~700Mbps），避免验收争议；
    （2）"传输峰值CPU<15%"未定义基准机型：8核手机上1核满载即12.5%，
         800Mbps加密+哈希可能贴线。建议改为"桌面端≤15%，移动端按代表机型实测"；
    （3）"扫描刷新≤500ms"：mDNS被动监听首次发现通常超过500ms，需主动probe，
         建议放宽至2秒或注明"已缓存设备列表刷新≤500ms"。

### 3.7 文件引擎边界情况缺失
    （1）接收端同名文件策略未定义（覆盖/自动重命名/询问）；
    （2）符号链接、管道、设备文件的跳过或转换策略未定义（文件夹递归必然遇到）；
    （3）Windows 260字符以上长路径、大小写不敏感文件系统的命名冲突处理；
    （4）磁盘空间应在任务启动前预检（文件总大小+安全余量），而非中途报-5终止。

### 3.8 依赖清单与正文不一致
    （1）4.2节列出 prost（protobuf），但正文协议为手工二进制格式——二选一，
         避免冗余依赖；
    （2）mdns-rs 维护活跃度一般，建议评估 mdns-sd 替代；
    （3）4.1节"全模块异步无阻塞"需补充：哈希计算、文件夹遍历为CPU密集任务，
         必须走 Tokio spawn_blocking，避免阻塞异步运行时。

### 3.9 隐私项
mDNS明文广播设备名/系统版本，同一局域网任何人可持续看到本机设备指纹。
建议增加"隐身模式/暂停广播"开关，实现成本低，建议纳入一期设置面板。

## 四、建议补充的内容

1. 接收确认交互流程（同意/拒绝/全部允许），安全与体验双重刚需；
2. 证书与设备身份管理：首次启动生成本地密钥对+证书、UUID持久化、配对码展示；
3. 协议版本协商完整规则：未知指令处理方式、最低兼容版本约定；
4. 测试策略（原文档自称"测试统一基准"但无任何测试方案），至少包含：
   协议层单元测试、报文解析模糊测试（fuzz）、弱网模拟（丢包/高延迟/断网恢复）、
   跨端兼容性矩阵、72小时稳定性测试的分平台执行细则；
5. 里程碑与分阶段验收标准（见第五节）。

## 五、落地路径建议（分阶段实施）

五端齐发风险极高，建议按以下阶段收敛：

阶段一（MVP）：Rust核心 + Tauri桌面端（Windows/macOS）
    协议、传输引擎、断点续传全部在此阶段打磨；桌面端平台约束最少、迭代最快。
    预估工期：1~2名有Rust网络编程经验的工程师，约2~3个月。
阶段二：Android端
    cargo-ndk接入、JNI/FFI联调、前台服务与MulticastLock适配。
阶段三：iOS端
    后台限制、Bonjour、沙盒文件交互，平台坑最多，放在最后。
阶段四（可选）：BLE辅助发现、WiFi Direct
    视真实用户反馈再投入。
全部五端含边界情况加固，总工期预估5~8个月。

## 七、结论

架构方向正确、技术框架可行。当前文档为"高分架构 + 低分协议与安全设计"的组合，
原文档第八章"无需补充额外调研即可启动开发"的结论过于乐观。

执行建议：先按第六节修订清单完成需求文档V2修订——重点是协议报文结构重构、
取消QUIC明文、补齐配对/接收确认安全模型、纠正iOS后台与构建工具链的事实性
错误——修订完成后再启动项目脚手架搭建与编码开发。
